## Review workflow
1. Read upstream docs, license and release/commit history; check security and compatibility.
2. Inspect existing project code and issues; define the actual missing capability (do not duplicate an existing solution).
3. Choose a measurable comparison on a representative task (accuracy/quality, latency, RAM/VRAM, development and operational cost).
4. Prototype in isolation with rollback and tests. Keep alternatives explicitly competing instead of integrating both.
5. Record **adopt / reject / defer**, rationale, and version in the project-specific issue. Only adopt through a separately scoped implementation task.

## Special compatibility notes
- `Simulations` currently uses browser JavaScript without a Godot engine. Terrain3D, Gaea, BeeHave, Godot Voxel and SimpleXTerrain are **architectural references only** unless a Godot client is deliberately introduced. MuJoCo assets require a separate compatible physics runtime.
- Hatchet vs DBOS are alternative durable-workflow approaches; compare with existing orchestration rather than integrating both.
- BoxMOT vs Norfair are tracking alternatives; establish baselines before choosing.
- SGLang generally assumes suitable GPU infrastructure and is not a default for low-RAM local execution.
- Do not assume research benchmarks are functional AGI components or medical-grade clinical validation.
