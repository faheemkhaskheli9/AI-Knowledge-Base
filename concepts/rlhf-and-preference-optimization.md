# RLHF and preference optimization (DPO, GRPO)

## Summary
After supervised fine-tuning, models are further optimised against a signal of "better vs worse" rather than a single reference answer. RLHF learns a reward model from human preference pairs and optimises the policy with RL; DPO skips the reward model and trains directly on preference pairs; GRPO samples groups of answers and uses relative rewards (often programmatic checks) to improve reasoning.

## Key concepts
- **RLHF pipeline**: SFT model -> collect ranked outputs -> train reward model -> optimise policy (PPO) with a KL penalty to the SFT reference so it does not drift.
- **DPO**: closed-form loss on (prompt, chosen, rejected) triples with a frozen reference model; stable, no sampling loop, no separate reward model. Related variants exist (IPO, KTO, ORPO, SimPO).
- **GRPO**: for each prompt sample G completions, score them, use the group-normalised reward as advantage; no value/critic model, lower memory than PPO. Introduced in DeepSeekMath.
- **RLVR (verifiable rewards)**: reward from a checker (unit tests, exact-match math answer, JSON schema validity) instead of a learned model. Basis of recent reasoning-model training (see [[reasoning-models]]).
- **Reward hacking**: the policy exploits flaws in the reward instead of doing the task.
- **RLAIF / constitutional methods**: an AI model provides the preference labels.

## When to use / scenarios
- DPO: you have thousands of preference pairs (from annotators, user thumbs-up/down, or LLM-judge) and want tone/safety/helpfulness shifts.
- GRPO/RLVR: tasks with automatic correctness checks: math, code, SQL execution match, format compliance.
- Real-world: a bank's assistant tuned to be concise and cautious on financial advice; a text-to-SQL model rewarded when the query returns the expected rows.
- Not when: SFT on good examples already solves it; there is no reliable preference/reward signal; you lack eval to detect regressions.

## Setup & code
`pip install trl transformers datasets` (APIs change between TRL versions; check the linked docs for yours.)

DPO:
```python
from datasets import load_dataset
from transformers import AutoModelForCausalLM, AutoTokenizer
from trl import DPOConfig, DPOTrainer

name = "Qwen/Qwen2.5-0.5B-Instruct"
model = AutoModelForCausalLM.from_pretrained(name)
tok = AutoTokenizer.from_pretrained(name)
ds = load_dataset("trl-lib/ultrafeedback_binarized", split="train[:500]")  # prompt/chosen/rejected
DPOTrainer(model=model, args=DPOConfig(output_dir="dpo-out", beta=0.1),
           train_dataset=ds, processing_class=tok).train()
```

GRPO with a programmatic reward (completions are strings for standard-format data):
```python
from datasets import load_dataset
from trl import GRPOConfig, GRPOTrainer

def short_reward(completions, **kwargs):           # one float per completion
    return [-abs(len(c) - 200) / 200 for c in completions]

ds = load_dataset("trl-lib/tldr", split="train[:200]")
GRPOTrainer(model="Qwen/Qwen2.5-0.5B-Instruct", reward_funcs=short_reward,
            args=GRPOConfig(output_dir="grpo-out"), train_dataset=ds).train()
```
Combine with LoRA via `peft_config=` to fit on one GPU.

## Choosing / trade-offs
- DPO (simple, offline, cheap) vs PPO-RLHF (online, flexible, complex and memory hungry) vs GRPO (online, no critic, needs generation throughput).
- Human labels (best quality, expensive) vs LLM-judge labels (cheap, inherits judge bias) vs programmatic rewards (precise, limited to checkable tasks).
- KL strength (beta): high stays close to the reference; low gains more but risks degeneration.

## Gotchas
- Preference data quality and chosen/rejected length bias: DPO tends to increase verbosity if chosen answers are longer.
- Off-policy drift: DPO pairs generated by a different model than the one being tuned give weaker gains; prefer on-policy samples.
- Reward functions that can be gamed (format-only rewards) will be gamed. Log samples, not just mean reward.
- RL runs are noisy; fix seeds, track KL and held-out evals ([[llm-evaluation]]).
- Always start from a decent SFT checkpoint; RL does not fix a model that cannot yet do the task.
